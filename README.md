# Частина 1

```text
+-------------------------+
|          :User          |
+-------------------------+
| (U) userId: Integer     |
|     gender: String      |
|     age: Integer        |
|     occupation: String  |
+-------------------------+
             |
             |  [:RATED]
             |  - rating: Integer
             |  - timestamp: Integer
             V
+-------------------------+
|         :Movie          |
+-------------------------+
| (U) movieId: Integer    |
| (I) title: String       |
|     year: Integer       |
+-------------------------+
             |
             |  [:IN_GENRE]
             V
+-------------------------+
|         :Genre          |
+-------------------------+
| (I) name: String        |
+-------------------------+
```

**Умовні позначення:**

**(U)** - Unique Constraint (Унікальний ідентифікатор).
**(I)** - Index (Індекс для швидкого пошуку)

**1. Які сутності стали вузлами, а які — ребрами? Чому?**
**Відповідь.** Вузли: User, Movie, Genre стали вузлами, оскільки є самостійними, фізичними сутностями (іменниками). Вони можуть існувати незалежно одне від одного. Кожна з цих сутностей має власний набір атрибутів (age у користувача, year у фільму, name у жанру), які описують саме цей об'єкт. Ребра: RATED (Оцінив) та IN_GENRE (Належить до жанру) стали ребрами, оскільки описують взаємодію або зв'язок між вузлами. ```[:RATED]``` — це подія (дієслово). Для оцінки обов'язково потрібен той, хто оцінює (User), і те, що оцінюють (Movie), тому сама оцінка (rating) і час (timestamp) стали властивостями цього ребра, оскыльки характеризують факт взаємодії між двома вузлами. ```[:IN_GENRE]``` — це зв'язок, який з'єднує сутність (Movie) з її категорією (Genre) для забезпечення швидкого обходу графа під час пошуку.

**2. Оцінка користувача за фільм — це ребро (User)-[:RATED]->(Movie) чи окремий вузол (Rating)? Аргументуйте своє рішення. Це не риторичне запитання: в обох підходів є реальні trade-off-и.**
**Відповідь.** Тут можна робити і як окремий вузол, так і як ребро, для даного завдання на мою думку логічнішим є саме властивість ребра. Так, один користувач може декілька разів оцінити один і той самий фільм, але в такому випадку буде створено декілька ребер від користувача до фільму. Маючи багато вузлів, граф стає громіздким, його важче візуалізувати. Крім цього щоб отримати базову інформацію, базі доведеться робити більше стрибків по графу, що уповільнює роботу. Робити окреми вузол Rating є сенс, якщо у майбутньому ми знаємо, що до нього будуть додаватися властивості.

**3. Чому жанри фільму вигідніше зберігати як окремі вузли (Genre), а не як список у властивості вузла Movie?**
**Відповідь.** Проаналізувавши завдання і запити до бази перед створенням графа, я дійшла висновку про те, що жанр буде буде фігурувати в деяких запитах. Оскільки в одного фільму може бути декілька жанрів, то тут вже виникає зв'язок 1 до багатьох. Саме тому доцільніше виокремити жанр як окрему сутність (вузол). Так запити до жанрів будуть легшими і швидшими.

**Що означає довжина шляху в даному контексті?**
Зв'язок між двома користувачами можливий через фільм. Він відіграє роль моста. Довжина має такий шаблон: Користувач -> Фільм -> Користувач.
**Один хоп — це один крок по ребру RATED, а значить — шлях довжини 2 означає, що два користувачі оцінили один і той самий фільм. Як інтерпретувати шлях довжини 4? Довжини 6?**

**Шлях довжини 4** означає, що 2 користувача (user 1 i user 2) не мають спільнопереглянутого фільму. Але є друг (user 3), який переглянув фільм, що дивився користувач 1 і другий фільм, що дивився користувач 2.  Це буде такий ланцюг: u1 -> m1 <- u3 -> m2 <- u2.

**Шлях довжини 6** означає, що 2 користувача (user 1 i user 2) не мають спільнопереглянутого фільму. Але є друг (user 3), який переглянув фільм, що дивилися user 1 і новий друг (user 4). Той в свою чергу дивився один і той самий фільм, що й користувач 2. Це буде такий ланцюг: u1 -> m1 <- u3 -> m2 <- u4 -> m3 <- u2.

**1. Граф vs SQL. Які із запитів частини 3 було б складно або неможливо написати в SQL? Чому? Наведіть конкретний приклад — покажіть, як виглядав би еквівалентний SQL-запит (або поясніть, чому його не існує).**
**Відповідь.** Найбільшу складність для реляційних баз даних SQL становлять запити, що вимагають багатокрокових обходів зв'язків та пошуку шляхів невідомої довжини. Із запитів частини 3 для SQL найскладнішим буде Запит 5 (Рекомендації), та практично неможливим для ефективного виконання — Запит 6 (Найкоротший ланцюжок зв'язку між двома користувачами). Відомо, що у графовій базі даних зв'язки зберігаються фізично як вказівники. Алгоритм проходить від вузла до вузла. У реляційній базі зв'язки обчислюються в момент виконання через операцію JOIN. Для Запиту 6 ми заздалегідь не знаємо, скільки проміжних кроків знаходиться між двома заданими людьми. В SQL не можна просто написати JOIN невідому кількість разів. Для цього в SQL використовують рекурсивні загальні табличні вирази WITH RECURSIVE, Проте на великих об'ємах даних (наприклад, 50 000 зв'язків) такий запит викличе експоненційне зростання проміжних таблиць, що призведе до тайм-ауту бази даних через брак оперативної пам'яті.
Приклад еквівалентного SQL-запиту для пошуку шляху довжиною до 3 кроків:
```
WITH RECURSIVE UserPaths AS (
    -- Базовий випадок (прямий зв'язок 1 крок)
    SELECT source_user, target_user, 1 AS depth
    FROM user_similarity
    WHERE source_user = 10
    
    UNION ALL
    
    -- Рекурсивний крок (додаємо наступні кроки)
    SELECT up.source_user, us.target_user, up.depth + 1
    FROM UserPaths up
    JOIN user_similarity us ON up.target_user = us.source_user
    WHERE up.depth < 3
)
SELECT * FROM UserPaths WHERE target_user = 5100;
```
**2. Де граф програє? Для яких задач із цим датасетом реляційна модель підійшла б краще? Наприклад: агрегація по всіх користувачах, звіти, експорт даних.**
**Відповідь.** Графова база даних (Neo4j) створена для навігації по зв'язках (обхід графа), але вона суттєво програє SQL у задачах глобальної агрегації та сканування всієї таблиці. Реляційні бази (особливо колонкові) оптимізовані для математичних операцій над цілими стовпцями даних.

Для цього датасету SQL підійшов би набагато краще, якби нам потрібно було: 
- **Згенерувати фінансові або статистичні звіти:** Наприклад, знайти середню оцінку для кожного з 10 000 фільмів у базі або порахувати загальну кількість користувачів, згрупованих за віком та статтю (GROUP BY age, gender). У Neo4j для обчислення середньої оцінки алгоритм має фізично "пройтися" по кожному вузлу Movie і кожному ребру RATED, що є дорогою операцією. В SQL це просте і швидке сканування одного індексованого стовпця.
- **Експорт даних та міграції:** Вивантажити плоску таблицю "Користувач - Фільм - Оцінка - Дата" у форматі CSV для подальшого навчання моделі машинного навчання (наприклад, у Python/Pandas) з SQL-бази значно простіше і швидше, оскільки дані вже зберігаються у вигляді плоских таблиць, тоді як граф потрібно розплутувати.

**3. Покращення схеми. Які зміни в схемі прискорили б конкретні запити з частини 3? Розгляньте хоча б два запити.**
**Відповідь.** Оскільки базова оптимізація пошуку вузлів вже реалізована на етапі створення схеми (існують індекси та обмеження унікальності для userId, movieId, title та name), подальше прискорення складних запитів з частини 3 може бути пов'язаним із структурними змінами у самому графі. 
 У запитах 3 та 5 нам потрібно знаходити фільми, які отримали високу оцінку (рейтинг >= 4). Наразі запит виглядає як ```MATCH (u)-[r:RATED]->(m) WHERE r.rating >= 4```. Двигун бази даних проходить всі ребра RATED (із низькими оцінками також), витягує з пам'яті їхні властивості і фільтрує. При великій кількості оцінок це сповільнює обхід графа. Щоб вирішити цю проблему можна змінити схему, додавши новий спеціалізований тип зв'язку для високих оцінок (наприклад, [:LIKED]): ```MATCH (u)-[r:RATED]->(m) WHERE r.rating >= 4 MERGE (u)-[:LIKED]->(m)```. Після цього Запит 3 перетвориться на ```MATCH (u1)-[:LIKED]->(m)<-[:LIKED]-(u2)```. База даних ігноруватиме всі низькі оцінки ще на рівні топології, що прискорить обхід у кілька разів.
